# Especificação e plano de implementação — Modo Code

**Status:** proposta aprovada para implementação  
**Data:** 2026-08-30  
**Escopo:** experiência de chat, runtime de agentes, testes, browser, Git e notificações do Orin.

## Resultado de produto

O Modo Code converte uma solicitação relacionada a software em uma execução orientada a evidências. Ele não termina apenas porque o modelo produziu código: o Orin planeja, obtém a aprovação necessária, implementa, cria ou atualiza testes, corrige falhas do escopo, valida visualmente alterações de frontend e apresenta um resultado verificável.

O usuário pode ativá-lo no chat ou o Orin pode sugeri-lo/ativá-lo ao reconhecer uma demanda de código. O modo também serve para investigação técnica, mas adapta o fluxo e não exige implementação ou commit nesse caso.

```text
detectar/ativar → avaliar escopo e rigor → salvar plano → aprovação
                                                        ↓
      entrega ← resumo/evidências ← validação ← testes ← implementação
                                    ↑              ↓
                                 correção ← falha no escopo
```

O Modo Code usa a `Execution` canônica e seus checkpoints. Ele não cria uma máquina de estados concorrente ao runtime de chat.

## Objetivos

1. Tornar explícito o plano, os critérios de aceite e as verificações antes de qualquer modificação.
2. Exigir testes automatizados para código alterado e impedir conclusão silenciosa com verificações relevantes em falha.
3. Exigir validação real em navegador para mudanças de frontend: fluxo afetado, responsividade, acessibilidade, screenshot e console.
4. Manter o usuário no controle de decisões, efeitos externos e ambiguidades, com uma política global de autonomia clara.
5. Registrar plano, evidências e ressalvas de forma durável e legível no chat.
6. Acompanhar operações longas em segundo plano e avisar o usuário no chat e, quando habilitado, por notificação do sistema.

## Fora de escopo inicial

- Substituir o CI do repositório ou garantir que provedores externos sejam determinísticos.
- Ignorar uma falha pré-existente para declarar sucesso. Ela exige decisão do usuário.
- Executar deploy de produção sem confirmação, inclusive em autonomia total.
- Exibir, persistir em planos, incluir em screenshots ou enviar em notificações qualquer segredo, token, URL sensível, cookie ou conteúdo confidencial.

## Ativação e classificação

### Ativação

O modo pode começar de duas formas:

- **Manual:** controle `Code` no compositor do chat; ele vale para a próxima solicitação e aparece no contexto do turno.
- **Automática:** o classificador local do runtime identifica intenção de implementar, corrigir bug, refatorar, integrar, revisar código ou investigar uma falha. Antes de planejar, o chat mostra o aviso discreto **“Modo Code ativado — vou preparar um plano”**, com a ação **“Usar chat normal nesta mensagem”**.

Ativação automática não é autorização para alterar arquivos. A política de aprovação continua sendo aplicada.

### Tipos de trabalho

| Tipo | Fluxo | Resultado mínimo |
|---|---|---|
| Implementação | plano → aprovação → implementar → validar | código, testes, evidências e resumo |
| Correção | reproduzir → plano → aprovação → corrigir → regressão | causa, teste de regressão e evidências |
| Refatoração | plano → aprovação → refatorar → regressão | equivalência verificada e alterações documentadas |
| Investigação | diagnosticar → reproduzir/verificar → relatar | causa/hipóteses, evidências e proposta; sem commit obrigatório |
| Revisão | inspecionar → verificar → relatar | achados priorizados e evidências; sem mudança por padrão |

### Rigor escolhido pelo agente

O Orin declara o nível sugerido no plano. O usuário pode alterá-lo antes de aprovar.

| Nível | Quando aplicar | Mínimos adicionais |
|---|---|---|
| Rápido | alteração pequena, localizada e reversível | plano curto, testes diretamente afetados e validação objetiva |
| Padrão | feature, correção relevante ou refatoração | cobertura nova/atualizada, regressão do módulo e browser para frontend |
| Rigoroso | autenticação, autorização, segredos, dados, pagamentos, arquitetura, integração crítica ou deploy | análise de impacto, testes de fronteiras/erros, validação ampliada, revisão de segurança e confirmações em marcos sensíveis |

O nível não reduz as regras inegociáveis: testes são obrigatórios para código modificado; frontend exige validação no browser; e deploy de produção sempre requer confirmação.

## Política de autonomia e confirmação

A preferência é global para o usuário — nunca inferida por projeto — e pode ser substituída por uma autorização explícita no pedido atual, por exemplo “pode seguir com autonomia”. A escolha e seu alcance devem aparecer no plano e no histórico da execução.

| Preferência | Plano | Código/testes/commit | Push, PR e deploy não produtivo | Deploy em produção |
|---|---|---|---|---|
| **Sempre pedir aprovação** | confirmar | confirmar após o plano | confirmar | confirmar |
| **Autonomia de código** | informar, sem bloquear | executar | confirmar | confirmar |
| **Autonomia total** | informar, sem bloquear | executar | executar | **confirmar sempre** |

Regras complementares:

- Uma instrução explícita de autonomia vale apenas para o pedido/continuação atual; não altera preferências globais.
- Ambiguidade material, conflito de produto, requisito de segurança não decidido ou falha pré-existente fora de escopo usa `ask_user`, salvo autorização explícita para que o Orin decida esse tipo de questão.
- Ações destrutivas, migrações irreversíveis, remoção de dados e interação externa continuam sujeitas à política existente de ferramentas e à confirmação quando exigida.
- `push`, criação de PR e deploy seguem a tabela; um commit local após todas as verificações é permitido nos níveis que autorizam execução de código.

## Planejamento e persistência

Antes de modificar arquivos, o Orin cria um plano e critérios de aceite. No primeiro uso de Modo Code em um repositório, pergunta via `ask_user` se `.orin/plans/` deve ser versionado ou ignorado pelo Git. A decisão é armazenada na configuração do workspace e, se for “ignorar”, o Orin propõe/adiciona a regra específica ao `.gitignore` somente com a aprovação aplicável.

O arquivo do plano é criado em `.orin/plans/<timestamp>-<slug>.md`; seu conteúdo inicial é persistido como artefato da `Execution` antes da aprovação. Atualizações de execução acrescentam o resultado ao mesmo arquivo, sem sobrescrever a intenção aprovada.

Modelo mínimo:

```md
# Plano: <título>

## Objetivo
## Escopo e fora de escopo
## Critérios de aceite
## Rigor e justificativa
## Etapas de implementação
## Estratégia de testes
## Validação visual
## Riscos, suposições e decisões pendentes
## Resultado da execução
```

O cartão de aprovação usa o `ask_user` existente, com opções **Aprovar plano**, **Pedir ajustes** e **Cancelar**. Para decisões de Git e ações externas, o cartão contextualiza alvo, impacto, branch e diff/resumo sanitizado.

## Fluxo operacional

### Implementação e correção

1. O runtime inspeciona apenas o contexto necessário: projeto, arquivos relevantes, convenções, comandos de teste, estado Git e capacidades do modelo/ferramentas.
2. Ele produz o plano, a classificação e critérios mensuráveis de aceite; se algo material for incerto, pergunta antes de propor mudanças.
3. Após a aprovação exigida, salva o plano, realiza alterações pequenas e coerentes e registra checkpoints de efeito.
4. Cria ou atualiza testes automatizados que exercitem a mudança. Se não existir infraestrutura de testes, monta a infraestrutura mínima compatível ou para e pede uma decisão de escopo; validação manual não substitui teste automatizado.
5. Executa testes relevantes primeiro e depois o conjunto definido pelo nível de rigor. Também executa formatação, lint, typecheck, build ou gates já configurados que sejam afetados pela mudança.
6. Falhas causadas pela alteração entram no loop `diagnosticar → corrigir → executar novamente`. Não há limite artificial de uma tentativa; limites de orçamento, tempo e segurança continuam visíveis.
7. Uma falha comprovadamente pré-existente ou fora de escopo pausa a execução em `WAITING_USER`, inclui a evidência e oferece alternativas (corrigir separadamente, aceitar o bloqueio, reduzir escopo ou cancelar). O Orin não escolhe nem mascara essa falha.
8. Depois de todas as validações exigidas passarem, cria um commit local com mensagem que referencia o objetivo e o plano. Push, PR e deploy obedecem à política de autonomia.

### Frontend: gate visual obrigatório

Quando arquivos, rotas, componentes, estilos ou critérios de aceite implicarem UI, o plano deve conter a matriz de validação. A execução não é concluída sem:

- iniciar ou reutilizar o ambiente local de modo seguro;
- abrir a rota/fluxo alterado no browser isolado;
- percorrer o fluxo afetado com interações reais;
- verificar layouts de largura compacta e ampla definidos pelo projeto (ou, se inexistente, 375 px e 1440 px);
- executar as verificações de acessibilidade disponíveis e tratar violações críticas ou sérias causadas pela mudança;
- verificar ausência de erros de console e de falhas de rede relevantes ao escopo;
- capturar screenshots como artefatos privados e vinculá-los ao resultado;
- corrigir automaticamente divergências encontradas que estejam dentro do plano aprovado e repetir a validação.

Quando o browser, o servidor local ou uma dependência necessária não puderem ser iniciados, o estado é **Aguardando decisão** ou **Concluído com ressalvas**, nunca **Concluído**. O resumo diferencia claramente o que foi verificado do que não foi.

### Investigações e revisões

Investigação usa o mesmo envelope de rigor, rastreabilidade e acompanhamento, mas termina após reproduzir ou verificar a hipótese e apresentar evidências. Não há exigência de mudança, testes novos ou commit. Se o usuário aprovar uma correção proposta, inicia-se uma nova fase de implementação com plano de alteração e as confirmações normais.

## Estados e resultados

Os estágios de Modo Code são uma projeção tipada do `Execution`, e não novos estados canônicos. A persistência deve registrar `code_stage`, `plan_ref`, nível de rigor, autonomia efetiva, checks e evidências.

```text
DISCOVERING → PLANNING → WAITING_APPROVAL → IMPLEMENTING → VALIDATING
                                                   ↑              │
                                                   └── FIXING ◄───┘
                                                            │
                                  MONITORING_LONG_RUNNING ◄─┘
                                                            │
              COMPLETED | COMPLETED_WITH_CAVEATS | WAITING_DECISION | BLOCKED
```

Mapeamento para `Execution`:

| Situação apresentada | Estado canônico | Regra |
|---|---|---|
| planejamento, implementação, validação ou correção ativa | `RUNNING` / `WAITING_TOOL` | etapas e progresso são eventos de atividade |
| aprovação, ambiguidade ou falha pré-existente | `WAITING_USER` | nenhum worker fica ocupado; resposta do usuário re-enfileira |
| processo monitorado sem ação imediata | `WAITING_TOOL` ou `PAUSED` recuperável | depende de job externo/checkpoint; nunca busy wait |
| concluído | `COMPLETED` | todos os gates aplicáveis passaram |
| concluído com ressalvas | `COMPLETED` | resultado possui `completion_kind=WITH_CAVEATS` e ressalvas não vazias |
| bloqueado por condição sem avanço seguro | `PAUSED` | tem motivo, evidência e ação necessária; pode voltar a `QUEUED` após resposta |
| erro interno/irrecuperável | `FAILED` | separado de bloqueio de produto/infraestrutura |

### Contrato de conclusão

O resumo final padronizado no chat inclui, sempre que aplicável:

1. **Estado:** concluído, concluído com ressalvas, aguardando decisão ou bloqueado.
2. **Mudanças:** objetivo, arquivos/áreas alteradas e commit local.
3. **Testes e qualidade:** comandos executados, resultado, cobertura/escopo e falhas excluídas por decisão do usuário.
4. **Validação visual:** rotas e fluxos percorridos, viewports, acessibilidade, console, screenshots e limitações.
5. **Riscos e ressalvas:** somente fatos relevantes, concretos e sanitizados.
6. **Próximos passos:** push, PR, deploy, decisão pendente ou nenhuma ação.

“Concluído com ressalvas” só é permitido quando a funcionalidade do escopo foi verificada e a ressalva decorre de limitação externa ou parte explicitamente não verificável. Não serve para contornar testes falhos atribuíveis à alteração.

## Monitoramento e notificações

Builds, suítes extensas, análise estática, testes de browser e jobs externos não devem prender um turno em espera ativa. O runtime grava o job/checkpoint, libera o worker e agenda um trigger de acompanhamento durável.

- A cadência começa entre 20 e 30 segundos; aumenta gradualmente para jobs longos estáveis e reinicia após uma mudança observável.
- O trigger revalida ownership, lease, cancelamento, deadline e idempotência antes de ler estado ou retomar trabalho.
- Eventos de progresso só aparecem no chat quando houver mudança material: início, marco, conclusão, falha, timeout ou necessidade de decisão.
- A notificação do sistema é opt-in nas configurações. Quando habilitada, ela é enviada para **conclusão**, **conclusão com ressalvas**, **falha/bloqueio** e **necessidade de decisão**. O texto não contém segredos, paths sensíveis, logs ou diff; clicar abre a conversa/execução correspondente.
- Se a aplicação estiver em foco, o chat é a fonte principal e a notificação pode ser suprimida por preferência para evitar duplicidade.

## Arquitetura proposta

### Domínio e persistência

Criar um módulo `agentos.code_mode` com contratos sem dependência de API/UI:

- `CodeModeRequest`: ativação, tipo de trabalho, workspace, autonomia efetiva e preferência de persistência de plano.
- `CodePlan`: objetivo, escopo, critérios, rigor, etapas, comandos/gates previstos, matriz visual, riscos e decisões.
- `CodeRunSnapshot`: etapa, status de conclusão, checks, tentativas, evidências, ressalvas, commit e ações externas pendentes.
- `ValidationCheck`: categoria (`test`, `lint`, `typecheck`, `build`, `browser_flow`, `a11y`, `console`, `screenshot`), comando/referência, resultado, timestamps, escopo e evidência.
- `CodeModePolicy`: autonomia global, notificações e regras que não admitem bypass.

Persistir a identidade e projeção do modo associadas a `execution_id`; guardar conteúdo grande (plano, saída de comandos, screenshots) como referência de artefato. Uma migration cria tabelas ou colunas de projeção, índices por `execution_id` e `workspace_id`, e mantém eventos/outbox na mesma transação que as transições relevantes.

A preferência de persistir `.orin/plans/` pertence à configuração do workspace; autonomia e notificações pertencem à configuração global do usuário. Segredos nunca são serializados em `CodePlan`, eventos públicos, notificações ou artefatos destinados à UI.

### Runtime e ferramentas

- O classificador de intenção é uma função determinística e conservadora sobre intenção + contexto; o modelo não pode elevar sozinho a política de autonomia.
- Uma capability/orquestrador do modo prepara o plano antes de expor ferramentas mutáveis. A guarda de ferramentas permite leitura para descoberta, mas bloqueia escrita, Git mutável e deploy até existir aprovação válida ou autonomia efetiva.
- As regras entram no prompt de execução como política, mas também são aplicadas na camada confiável de capacidade/tool runtime.
- O executor de validação interpreta comandos existentes no projeto de uma lista limitada/revisável; não usa texto de modelo como comando privilegiado. Cada processo tem limite, diretório validado, streaming de saída sanitizado, cancelamento e resultado durável.
- Integrações Git distinguem `status/diff/log` (leitura), `commit` (permitido pela política de código) e `push/PR/deploy` (efeitos externos com gate). O estado real do repositório é revalidado imediatamente antes de cada efeito.
- A validação visual compõe o `BrowserService` e o worker isolado já existentes. Novas ações de observação de console, viewport e relatório de acessibilidade devem ser tipadas e limitadas; screenshots permanecem artefatos privados.

### API, eventos e interface

Adicionar APIs autorizadas para iniciar/consultar Modo Code, obter plano e evidências, responder aprovações e ajustar preferências. A forma exata segue as convenções HTTP existentes, mas o contrato deve suportar reidratação da conversa e idempotência do botão de aprovação.

Eventos públicos mínimos:

- `code_mode.activated`, `code_mode.stage_changed`, `code_mode.plan_ready`;
- `code_mode.approval_requested`, `code_mode.approved`, `code_mode.decision_required`;
- `code_mode.validation_started`, `code_mode.validation_finished`, `code_mode.visual_evidence_ready`;
- `code_mode.monitoring_started`, `code_mode.monitoring_progress`, `code_mode.notification_sent`;
- `code_mode.completed`, `code_mode.completed_with_caveats`, `code_mode.blocked`.

Na interface, implementar:

- alternância `Code` no compositor e aviso de ativação automática com opção de desativar por mensagem;
- cartão de plano e aprovação reutilizando o padrão de `ask_user`;
- timeline de etapas com estados claros e sem transformar logs em ruído;
- cartões compactos para gates, evidências de browser e decisão pendente;
- resumo final padronizado, reidratável por SSE/histórico;
- Settings globais: nível de autonomia, notificações do sistema e preferências de acompanhamento;
- diálogo inicial por workspace para versionar ou ignorar `.orin/plans/`.

Todos os componentes devem ser navegáveis por teclado, anunciar mudança de estado de forma acessível e evitar que uma atualização de progresso roube foco do usuário.

## Plano de implementação

As fases abaixo são sequenciais por dependência. Cada fase fecha somente com seus testes e critérios verdes.

### Fase 0 — Contratos, policy e baseline

- Mapear os pontos atuais de entrada de chat, `ask_user`, `Execution`, atividades/SSE, configurações, terminal, browser e Git.
- Criar os modelos puros de `agentos.code_mode`, transições válidas e serialização sanitizada.
- Adicionar preferências globais de autonomia e notificações; criar a configuração de workspace para a política de `.orin/plans/`.
- Escrever testes de domínio para autonomia, decisões obrigatórias, exceção de produção, rigor e classificação conservadora.

**Aceite:** nenhum caminho mutável pode receber autorização apenas de texto/modelo; cada combinação de política é testada; segredos não aparecem na serialização.

### Fase 1 — Planejamento, aprovação e persistência

- Implementar a capability que descobre contexto, monta o plano e grava sua referência/metadata junto da `Execution`.
- Acrescentar o primeiro diálogo de persistência de planos por workspace.
- Integrar o cartão de plano ao `ask_user`, com reidratação, ajuste, cancelamento e resposta idempotente.
- Adicionar a guarda de ferramentas mutáveis e testes de tentativa de escrita antes de aprovação.

**Aceite:** uma tarefa de código gera plano em `.orin/plans/`, entra em `WAITING_USER` quando a política exige e não altera o workspace antes da decisão válida.

### Fase 2 — Execução, testes e ciclo de correção

- Implementar descoberta segura de comandos de teste/qualidade e execução com checkpoint, timeout, cancelamento e saída sanitizada.
- Exigir teste novo/atualizado como gate para mudanças de código; detectar projeto sem infraestrutura e abrir decisão de usuário.
- Modelar checks, tentativas e classificação de falha própria versus pré-existente; integrar o loop de correção somente para falhas do escopo.
- Integrar commit local após todos os gates; criar gates de confirmação para push, PR e deploy.

**Aceite:** testes de regressão provam que falha própria aciona correção, falha pré-existente pausa para decisão, e push/PR/deploy nunca escapam da política.

### Fase 3 — Browser, acessibilidade e evidências visuais

- Estender o contrato tipado do browser para viewport, leitura segura de console, coleta de resultados de acessibilidade e screenshot.
- Implementar matriz de validação visual, associação de screenshots/artifacts à execução e cartão de evidência no chat.
- Garantir correção e revalidação automática de defeitos no escopo aprovado.
- Criar fixtures locais de frontend para testar fluxo, viewport, console, a11y, browser indisponível e reidratação.

**Aceite:** uma alteração visual não conclui sem fluxo, duas larguras, screenshot, console e a11y; defeitos induzidos são detectados, corrigidos e verificados novamente.

### Fase 4 — Monitoramento durável e notificações do sistema

- Implementar job/checkpoint de acompanhamento e trigger com backoff, lease/fencing e recuperação após reinício.
- Projetar eventos de progresso material, sem polling ativo no worker de chat.
- Criar adaptador de notificação para desktop e fallback web; aplicar preferências, deduplicação e deep-link para a execução.
- Testar conclusão, bloqueio, decisão pendente, app em foco, preferência desligada e restart no meio do monitoramento.

**Aceite:** tarefa longa libera o worker, continua observável após restart e emite no máximo uma notificação por mudança terminal/decisória.

### Fase 5 — UX completa, segurança e release

- Implementar alternância Code, aviso automático, progresso, plano, cards, resumo e Settings com testes de acessibilidade.
- Fazer auditoria de autorização, isolamento de workspace, artefatos, logs e notificações.
- Adicionar testes unitários, integração, E2E do fluxo completo e browser real; documentar configuração e runbook.
- Rodar os gates do repositório, `git diff --check` e um cenário manual de ponta a ponta antes da release.

**Aceite:** cenários de implementação, investigação, autonomia, frontend, falha pré-existente, ressalva, cancelamento e notificação são aprovados em E2E; o resumo final é consistente após reload.

## Matriz de testes obrigatória

| Camada | Casos essenciais |
|---|---|
| Domínio | classificação, rigor, autonomia, regras invioláveis, estados e ressalvas |
| Persistência | atomicidade de plano/checkpoint, reidratação, tenancy, outbox, dados sanitizados |
| Runtime/tools | bloqueio pré-aprovação, retry seguro, cancelamento, falha pré-existente, comandos permitidos |
| Git/efeitos | commit permitido, push/PR/deploy confirmados, revalidação de estado e idempotência |
| Browser | fluxo, viewport, console, a11y, screenshot privado, host/artefato isolados |
| Monitoramento | backoff, restart, cancelamento, deduplicação e notificação |
| Frontend | cartão de plano, teclado, estados, SSE/reload, preferências e deep-link |
| E2E | fluxo completo de feature e cenário concluído com ressalvas |

## Métricas e observabilidade

- taxa de execuções Code que chegam a `COMPLETED` versus `COMPLETED_WITH_CAVEATS`, `WAITING_USER`, `PAUSED` e `FAILED`;
- tempo por etapa, número de iterações de correção e taxa de gates que falham;
- proporção de mudanças de frontend com evidência visual completa;
- número de notificações por execução e taxa de cliques/deep-link;
- tentativas bloqueadas antes de aprovação e violações de policy;
- nenhum plano, evento, log ou notificação com segredo detectável nos testes de regressão.

As métricas são agregadas/sanitizadas e não substituem a auditoria por execução.

## Decisões fechadas

- Aprovação usa o `ask_user` já existente.
- O Orin pede aprovação por padrão; autonomia é explícita no pedido ou definida globalmente em três níveis.
- O usuário decide, no primeiro uso de cada workspace, se `.orin/plans/` entra no Git.
- Testes automatizados são obrigatórios para código modificado.
- Frontend exige fluxo no browser, responsividade, acessibilidade, screenshot e console; divergências do escopo são corrigidas automaticamente.
- Falha pré-existente/fora de escopo pausa para decisão.
- Commit local pode ser automático conforme a política; push, PR e deploy exigem confirmação, salvo autonomia, e produção sempre confirma.
- Processos longos são acompanhados por trigger durável e podem gerar notificação do sistema.
- Os resultados possíveis são concluído, concluído com ressalvas, aguardando decisão e bloqueado.
