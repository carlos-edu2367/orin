# Plano do Kernel único de execução — 2026-08-26

- Antes da Fase 1, o chat de produção não usava o Kernel genérico como autoridade: `PostgresChatStore.create()` persistia o turno/fila; `ChatApplication._project_execution()` criava `Execution` em melhor esforço; `ChatWorker` executava `AgenticTurnRuntime` e projetava transições por `ExecutionApplicationAdapter` tolerando falhas. A criação atômica e o gate inicial do worker foram implementados depois em `2026-08-26-atomic-chat-execution-command.md`.
- `ExecutionControlService` já oferece a base durável (ownership, CAS, idempotência, transição, commit e outbox), e `RuntimeService` já organiza contexto/provider/action/orçamento/checkpoint. A migração deve evoluir essas portas, sem introduzir um terceiro loop de runtime.
- O plano registrado em `docs/plans/2026-08-26-unificacao-kernel-execucao-e-recuperacao.md` propõe: criação transacional de turn + Execution + dispatch + outbox; dispatch com lease/fencing; journal persistente de efeitos; checkpoints por referência; adaptador conversacional; recovery/reconciliação; rollout por feature flag para novos turns.
- Semântica obrigatória de recovery: efeito confirmado nunca é repetido; efeito não iniciado pode rodar; resultado indeterminado vira `UNKNOWN` e exige reconciliador/decisão humana, não retry automático. Checkpoints não guardam segredo nem dumps de memória e são gravados na mesma transação de decisões seguras.
- A transição preserva compatibilidade de chat, scheduler, atividade/SSE, Skills, memória, retrieval, browser, MCP, plugins e subagentes. `conversation_*` torna-se projeção/read model, enquanto `Execution` passa a ser a autoridade de lifecycle.
