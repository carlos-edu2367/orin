- Scope: `git diff 2353df2..HEAD` (12 commits, `a2cc386` to `93b0d36`) on `feat/orin-code-parity-w0-w3`.
- Reviewed against: `docs/superpowers/plans/2026-10-18-w1-permissions-security.md` (incl. its Deviations), the ledger `2026-10-18-w1-permissions-security-ledger.md`, master spec §4, and the W0 review (PRE-1 follow-up). REA source list in `claude-re-specs/03-...md` §1.3.
- Method: read every changed line, then attacked the engine, shell analyzer, path matcher, trust store, grants/request channel and auto-mode classifier with throwaway scripts kept outside the repo, cross-checking each decision against what the real tool (`ConversationWorkspace.resolve`, `/bin/sh`, NTFS) actually does.

## Summary verdict

**Not ready for W2. PRE-1 is fixed, but the new engine can be talked out of its deny rules and protected paths.** The pipeline order (deny → plan → ask → protected → allow → built-ins → mode) is right, the trust gate now governs repo rules through `EffectiveSettings` (PRE-1 closed — a cloned repo's `permissions.allow` no longer auto-allows), grants moved out of the repo, and the whole suite is green (`2686 passed, 52 skipped`; targeted `912 passed, 5 skipped`; frontend `596 passed`). But the security value of a `deny`/`ask` rule and of the protected-path list depends on the engine normalizing a command or path the **same way the tool that runs it does**, and in several places it does not:

1. **An allow rule executes appended commands** (`git status \ #; rm -rf ~`): the analyzer mis-lexes `#` after an escaped space/tab as a comment and drops the rest of the line, which `/bin/sh` then runs. (R1)
2. **Deny command rules are matched on the literal first token** — `/bin/rm`, `\rm`, `"rm"`, `command rm`, `env rm`, `rm.exe`, and `RM`/`DEL`/`GIT` on Windows all slip past a `Bash(rm:*)`/`Bash(del:*)` deny, which is supposed to win over everything including bypass. (R2)
3. **Path rules and protected paths are bypassed by leading `/`, `\`, `//` and trailing space** — the engine treats them as "outside" or "not protected" while `ConversationWorkspace.resolve` strips them and reads/writes the real `.env` / `.git/hooks`. (R3)
4. **acceptEdits `cp`/`mv` reach protected dirs** via `--target-directory=.git/hooks`, `.gi?`, `".g"it`, `.\git` — the token scan drops `-` options and never canonicalizes. (R4)
5. **An untrusted repo steers the auto-mode classifier** — `autoMode.*` is not in the untrusted filter, so repo text is injected into the security model's prompt and even picks its model. (R5)
6. **A process inside the workspace can forge a permission reply** and persist a permanent `allow` grant, defeating the point of moving grants out of the repo. (R6)

R1–R4 are the must-fix set for W2. They are not theoretical: each was reproduced, and R1/R3/R4 were confirmed against the real shell / filesystem.
