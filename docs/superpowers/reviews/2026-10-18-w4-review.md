## Must fix before W5

### W4-R1 — high — a server applies `permissions.additionalDirectories` although host folders are closed

- **Where:**
  - `src/agentos/agentic/session.py` `_additional_directory_sources` / `_apply_working_directories`, called from `build_runtime`;
  - `src/agentos/workers/chat.py` builds `TurnSession` with `enable_terminal=self._capabilities.shell` but nothing for `host_folders`;
  - `src/agentos/agentic/directories.py` `check_directory`.
- **What is wrong:**
  - Deviation 19 closes `/add-dir` on a server: the routes carry `capability("host_folders")`.
  - The turn, however, also takes folders from `permissions.additionalDirectories`, and a repository layer may set that key once its workspace is trusted.
  - On a server a profile controls its own workspace (import, bind, trust).
  - `check_directory` only refuses roots, the home folder and its ancestors, credential folders and Orin's own folders, so any other host folder becomes readable and, under the default `accept_edits`, editable by the file tools.
- **Failure scenario:** on a shared server (`host_folders=False`, `shell=False`), a profile imports a project whose `.claude/settings.json` lists a host folder, trusts it, and its agent then reads and edits files outside its sandbox.
- **Reproduced:**
  - `$R/agent_api/d01_server_mode_additional_dirs.py` uses the real server-mode app. It prints `POST /directories: 404`, then `additional_roots: (…drivers\etc, …)`, `Read host file: succeeded`, `Write host file: succeeded`. The write goes to a temp stand-in folder.
  - `$R/r09_server_additional_dirs.py` prints `host_folders = False … additional roots applied on a server: [..., 'C:/ProgramData']`.
- **Fix:**
  - `TurnSession.__init__` gains `host_folders: bool = True`, and `ChatWorker` passes `host_folders=self._capabilities.host_folders`.
  - When it is False, `_apply_working_directories` sets `additional_roots = ()` and reads neither the settings nor the store, announces nothing and adds no reminder.
- **Tests:** a unit test with `host_folders=False` and a trusted repository listing a real folder: `additional_roots == ()`, and a Read of a file there fails.

### W4-R2 — high — protected-path detection misses PowerShell `-Name:value` parameters and wildcard paths

- **Where:**
  - `src/agentos/permissions/engine.py` `_command_tokens`: splits `--name=value` but not PowerShell's `-Name:value`;
  - `_mentions_protected` / `_inside_unprotected`: a token with glob characters is compared literally;
  - `src/agentos/permissions/powershell.py` `analyze_powershell`: marks neither form as complex.
- **What is wrong:**
  - The protected check (`.git/`, `.claude/`, `.orin/` settings, the dotfile list) must make such a write ask a person (`requires_human`), even when an allow rule matches.
  - The check misses `Set-Content -Path:.git\config …` and a wildcard path such as `.gi?\config`, so an ordinary allow rule like `PowerShell(Set-Content:*)` approves the write.
  - In auto mode the classifier, not a person, decides.
  - The same wildcard gap exists for Bash file commands (`cp x .gi?/config` under an allow rule).
- **Reproduced:**
  - `$R/r01_ps_protected_paths.py`: for each spelling, the engine decision next to what real PowerShell does in a scratch folder.
    - The control `-Path .git\config` gives `ask requires_human=True`.
    - `-Path:`, `-LiteralPath:`, `-Destination:` and `.gi?`/`.gi*` give `allow requires_human=False`, and PowerShell really writes the protected file.
  - `$R/r01c_ps_protected_auto_mode.py`: in auto mode the `-Path:` forms reach the classifier.
  - `$R/r01b_bash_glob_control.py`: `cp evil.json .gi?/config` gives `allow`.
- **Fix:**
  1. `_command_tokens` also yields the value of a `-Name:value` token, for PowerShell and for any token starting with a single `-`.
  2. For protection purposes, a path token containing `*`, `?` or `[` is protected when its pattern could match a protected name. Simplest fail-closed rule: any glob in a token whose literal prefix contains a protected component's first characters, or any glob at all in a write target, makes the call ask with `requires_human=True`.
  3. `analyze_powershell` marks `-Name:value` with a path-like value as complex.
- **Tests:** engine tests for the spellings above (PowerShell and Bash), each expecting `ask` with `requires_human=True` under an allow rule, in `ask_permissions`, `accept_edits` and `auto`.

### W4-R3 — medium — Monitor and PowerShell skip safety nets that Bash has

- **Where:**
  - `src/agentos/permissions/auto_mode.py` applies `DEFAULT_HARD_DENY_PATTERNS` only to `{"run_command", "powershell"}`;
  - `src/agentos/agentic/tools/_shared.py` `_BLOCKED_COMMAND` knows only cmd/bash idioms.
- **What is wrong:**
  - Monitor runs a shell command, but in auto mode its commands are never checked against the hard-deny list; they go straight to the classifier.
  - The host-protection block refuses `shutdown`/`rd /s /q C:\` but not the PowerShell equivalents (`Stop-Computer`, `Restart-Computer`, `Format-Volume`, `Clear-Disk`, `Remove-Item -Recurse … C:\`, download-and-run through `iwr … | iex`).
  - The hard-deny list does not know them either.
- **Reproduced:**
  - `$R/r02_monitor_auto_hard_deny.py`: the same three commands give `deny` for Bash and PowerShell, and `allow` (classifier) for Monitor.
  - `$R/r13_host_block_powershell.py`: a regex-only check, nothing is run. Every PowerShell spelling gives `blocked_by_host_guard=False auto_mode_hard_deny=False`.
- **Fix:**
  - Use `rules.SHELL_TOOLS` (which includes `monitor`) wherever auto mode or the classifier size check tests for shell tools.
  - Add the PowerShell host-destructive cmdlets and the `iwr|irm … | iex` pattern to both `_BLOCKED_COMMAND` and `DEFAULT_HARD_DENY_PATTERNS`. Match case-insensitively, and match `Remove-Item` with recursion on a drive root.
- **Tests:** parametrised over `run_command`/`powershell`/`monitor` × the commands above: hard-deny in auto mode, and the toolset refuses them before running.

### W4-R4 — medium — deny rules are evaded by shell escape characters (bypass mode)

- **Where:** `src/agentos/permissions/powershell.py` (`analyze_powershell`) and `src/agentos/permissions/shell.py` (the Bash analysis), as consumed by `PermissionEngine.decide`.
- **What is wrong:**
  - A deny rule must hold in every mode, including `full_autonomy`.
  - PowerShell's escape character (backtick) inside a command name makes the analysis see a different program than PowerShell runs: `r`m` and `Remove-It`em` are allowed under `PowerShell(Remove-Item:*)` and `Bash(rm:*)`, and they really delete.
  - The Bash analysis has the same class of gap: a backslash inside the program name, and a nested `sh -c '…'`, are allowed under `Bash(rm:*)`. The first spelling predates W4.
- **Reproduced:** `$R/r06_deny_escapes.py` (deletes only a scratch file). PowerShell `'r`m victim.txt' -> allow deletes=True`; Bash `'r\m victim.txt' -> allow`, `"sh -c 'rm victim.txt'" -> allow`.
- **Fix:**
  - Both analyses mark a word containing an escape character (PowerShell backtick; a Bash backslash outside quotes in the program position) as complex.
  - Both treat a nested shell (`sh|bash|zsh -c`, `powershell|pwsh -Command`, `cmd /c`) as complex unless its inner command is analysed recursively.
  - In `decide`, when a deny or ask rule exists for the tool and the analysis is complex, the result is `ask` with `requires_human=True` in every mode. It is never `allow`: a rule the engine cannot evaluate must not be bypassed.
- **Tests:** the five spellings above under a deny rule in `full_autonomy`: none may be `allow`.

### W4-R5 — medium — the Code-mode `git push` / `gh pr` guards are regexes on the raw command

- **Where:** `src/agentos/agentic/agent_tools.py` `_invoke_unobserved`: `re.search(r"\bgit\s+push\b", …)` and the `gh (pr|repo)` and deploy checks.
- **What is wrong:**
  - The guard is the last line before a push in Code mode without push permission.
  - Valid spellings with git's global options (`git -C . push`, `git --no-pager push`, `git.exe push`) do not match, so the push runs.
- **Reproduced:** `$R/r07_push_guard_spellings.py`, against a bare local remote in a temp folder. `git push …` gives `CODE_PUSH_CONFIRMATION_REQUIRED`; `git -C . push`, `git.exe push` and `git --no-pager push` succeed and create branches on the remote.
- **Fix:**
  - Decide from the shell analysis (`analyze_for(command, dialect)`), not the raw text.
  - A subcommand is a push when its program, without a `.exe` suffix and case-insensitively, is `git`, and its first non-option word is `push`. Skip git's global options: `-C <dir>`, `-c <k=v>`, `--git-dir[=…]`, `--work-tree[=…]`, `--no-pager`, `--namespace[=…]`, `-P`.
  - Apply the same treatment to `gh pr|repo` and to the deploy words.
  - A complex analysis that mentions `push` anywhere is treated as a push (fail closed).
- **Tests:** the spellings above for Bash, PowerShell and Monitor; each refused without push permission and allowed with it.

### W4-R6 — medium — Bash `cwd` inside an additional directory runs the command and then fails

- **Where:** `src/agentos/agentic/tools/shell/bash.py` `_remember_session_cwd` and the cwd reporting near the end of `_run_shell`. Both call `relative_to(self.workspace.root)`. Also `_resolve_cwd_after_command`, which refuses a `cd` that stays inside an added folder.
- **What is wrong:** `cwd` in an added folder is accepted by `workspace.resolve`, so the command runs. Recording the new cwd then raises `ValueError`, and the call reports `TOOL_FAILED` after the side effect. Every later call fails the same way, and `cd sub` inside the added folder is refused.
- **Reproduced:** `$R/r03_bash_cwd_in_added_dir.py`. The output shows `call 1: failed TOOL_FAILED | ValueError … is not in the subpath …`, `counter.txt in the added folder: ['run-1', 'run-2']` (it ran twice), and `call 3 (cd sub …): failed TOOL_REFUSED`.
- **Fix:**
  - Store and report the session cwd through `workspace.key()`: relative under the root, absolute under an added folder.
  - Restore it through `workspace.resolve()`.
  - `_resolve_cwd_after_command` accepts a cd target inside any working directory.
- **Tests:** Bash with `cwd` in an added folder succeeds once and records the cwd. A second call runs there. `cd sub` inside it is accepted. A `cd` outside every working directory is still refused.

### W4-R7 — medium — a scheduled run answers the conversation's pending question or approval

- **Where:**
  - `src/agentos/scheduler/scheduled_chats.py` `_materialize` creates the turn through `PostgresChatStore.create`;
  - `src/agentos/conversations/chat.py` `create` closes every `waiting_user` turn of the conversation.
- **What is wrong:**
  - A run started by ScheduleWakeup, CronCreate or a Monitor wake, all of which carry model-written text, can fire while the conversation waits on an AskUserQuestion or a plan approval.
  - The pending prompt is then marked completed, and the scheduled message becomes the next "user" message: the model can effectively answer its own approval request.
  - Schedules-page runs have the same effect on a pending question.
- **Reproduced:** `$R/r05_wake_closes_question.py`. A turn waits for approval and a wakeup fires. The transcript then shows the question turn completed, followed by a queued turn whose user message is the wakeup's prompt.
- **Fix:**
  - In `run_due`, a schedule bound to a conversation that has a `waiting_user` (or running/queued) turn is not materialized. The occurrence is released and retried at the next poll; for tool-made schedules it is retried at most once per minute.
  - A scheduled message never resolves a waiting turn: the "close waiting turns" step in `create` is skipped when `scheduled_by_schedule_id` is set.
- **Tests:** a scheduler test that a due wakeup does not create a turn while the conversation waits, and does once it stops waiting. A chat-store test that a scheduled create leaves a waiting turn waiting.

### W4-R8 — medium — a recurring schedule replays every missed fire after downtime

- **Where:** `ScheduledChatService.run_due`: `next_at = self._next_after_rule(rule, tz, logical_at)` advances from the missed time, not from now.
- **What is wrong:** after the machine slept or Orin was closed, a `*/5` cron job fires once per poll for every missed slot. 3 hours of downtime produce 36 turns. The same is true of the existing `hourly` rule.
- **Reproduced:** `$R/r10_cron_catch_up.py`: `after a 3 h gap, 50 polls fired 36 occurrences and queued 36 turns`.
- **Fix:** advance with `next_at = next occurrence strictly after max(logical_at, now)`. A run that was missed while Orin was down fires once (coalesced), then the schedule continues from now.
- **Tests:** a 3-hour gap produces exactly one materialized occurrence, and `next_fire_at` is in the future.

### W4-R9 — medium — Monitor output floods the next model request and crowds out other reminders

- **Where:**
  - `src/agentos/agentic/tools/scheduling/monitor.py` `_deliver_locked`, which adds one reminder per delivery;
  - `src/agentos/agentic/reminders.py`: `ReminderQueue` holds at most 32 items.
- **What is wrong:**
  - A busy monitor fills the whole queue (32 reminders, about 122,000 characters in one request), and any other reminder (a file that changed, a todo or plan-mode notice) is then dropped.
  - A monitor started by a subagent attaches to the subagent's queue. When the subagent ends, its lines go to wake turns that are scheduled while the parent turn is still running.
- **Reproduced:**
  - `$R/r11_monitor_floods_reminders.py`: `pending reminders: 32 (all monitor: True), next request gets 122,425 characters` and `a file-changed reminder added now is accepted: False`.
  - `$R/r14_subagent_monitor.py`: `parent reminders received: []`, and a wake turn was scheduled during the running turn.
- **Fix:**
  - Coalesce: at most one pending monitor reminder per monitor. New lines replace or extend it, bounded by `MAX_EVENT_CHARS`, with the omitted count updated.
  - Cap all monitor reminders per request at a fixed budget, for example 12,000 characters in total.
  - Reserve queue capacity for other kinds: monitor items may take at most half of `MAX_PENDING_REMINDERS`.
  - A subagent's monitor uses the main turn's reminder queue, which the session passes down, and never schedules a wake while that turn is running.
- **Tests:** 200 lines in a burst give one reminder within budget, and a file-changed reminder is still accepted. A subagent monitor's lines reach the parent queue and no wake schedule is created while the turn runs.

### W4-R10 — high — a rewind can destroy current content it could not back up, and can apply half-way

- **Where:** `src/agentos/code_mode/file_history.py` `rewind`. It takes an undo snapshot of each file, then restores file by file.
- **What is wrong:**
  - When a file's current content cannot be captured for the undo (larger than the backup limit, or the history folder is not writable), the rewind still deletes or overwrites it. That content is then gone for good.
  - When one file's backup is missing, the others are restored anyway, leaving a tree that matches neither state.
  - At write time a Write over a file too large to back up gives no warning.
- **Reproduced (all in temp folders):**
  - `$R/agent_history/r01_undo_gap_large.py`: a file over the size limit is deleted by the rewind, and the undo then reports it skipped.
  - `$R/agent_history/r02_undo_fails_ioerror.py`: the undo snapshot write fails, the rewind raises part-way, and a restored file has already been changed.
  - `$R/agent_history/r05_half_apply.py`: `restored: ['api.py'] deleted: ['helpers.py'] skipped: [('client.py', 'its backup is missing')]`, leaving an inconsistent tree.
  - `$R/agent_history/r16_write_over_large_file.py`: no warning, and the rewind skips the file.
- **Fix:**
  - Make the rewind two-phase. First a preflight over every file to touch: its backup exists and matches its checksum, its directory checks pass, and its current content was captured in the undo manifest (blob written and fsynced). If any check fails, abort before writing anything and report why. Only then apply.
  - A file whose current content is too large to capture blocks the rewind, unless the API is called with an explicit `force_unbacked: [paths]` list. That list is for W7's interface, so for now: always block.
  - A Write or Edit over a file too large to back up says so in its result: "this file cannot be rewound".
- **Tests:** the four scenarios above. Nothing on disk changes when the preflight fails, and the response names the blocking file.

### W4-R11 — medium — a rewind races turns in other chats that share the folder, and its own check is check-then-act

- **Where:** `src/agentos/api/gateway.py` `_turn_in_flight`, which only looks at the rewound conversation, and both rewind routes.
- **What is wrong:**
  - Project chats share one workspace folder. Rewinding chat A while chat B's turn writes in the same folder returns 200 and changes files under B.
  - Within one conversation, a turn that starts between the busy check and the restore is not blocked.
- **Reproduced:**
  - `$R/agent_history/r15_sibling_conversation_running.py`: `rewind in chat A while chat B runs in the same folder: 200`.
  - `$R/agent_history/r12_turn_in_flight_race.py`: `rewind: 200 | turn state now: running`.
- **Fix:**
  - Take a per-workspace lock (an in-process lock keyed by the normalized workspace root, plus a row lock or advisory flag in the store for multiple processes). Hold it for the whole rewind.

  - The busy check covers every conversation bound to the same workspace root.
- **Tests:** the two scenarios: 409 while a sibling chat runs, and a turn cannot start while a rewind holds the lock.

### W4-R12 — high — a rewind follows a junction or link that replaced a working directory

- **Where:** `src/agentos/code_mode/file_history.py` `_restore`. `_inside(target, roots)` is lexical and only the immediate parent is checked for links.
- **What is wrong:** if a working directory, or the workspace root itself, is replaced by a junction after the turn, the rewind's restore and delete follow it and act on files at the junction's destination, outside every working directory.
- **Reproduced (temp folders only):**
  - `$R/agent_history/r04_added_dir_junction.py`: an added folder swapped for a junction. The rewind deletes `victim/sub/important.docx` and creates `victim/deep/f.txt` at the destination.
  - `$R/agent_history/r04b_workspace_root_junction.py`: the workspace root swapped. The turn's tools refuse, but the rewind deletes at the destination.
- **Fix:**
  - At rewind time, resolve each root strictly and refuse a root whose resolved path differs from its recorded path (it was replaced).
  - For each target, resolve its parent strictly and require it inside the resolved roots.
  - Refuse when any component between the root and the target is a link or junction (`os.path.islink` / `Path.is_junction`).
  - The API passes roots as recorded with the history, not re-resolved from a possibly replaced folder.
- **Tests:** both scenarios on Windows with `_winapi.CreateJunction` (skipped elsewhere). Nothing outside the original folders changes, and the files are reported skipped with a reason.

### W4-R15 — high (server) / medium (desktop) — WebFetch's address check and its connection resolve the host separately

This existed before W4. W4's WebFetch rework kept the guard unchanged.

- **Where:**
  - `src/agentos/agentic/tools/_shared.py` `_public_url`: `socket.getaddrinfo(host)` validates the addresses;
  - `src/agentos/agentic/tools/web/fetch.py` `_fetch_page`: httpx resolves the host again when it connects.
- **What is wrong:**
  1. The check and the connection are separate lookups. A name whose answer changes between them, or a non-ASCII name that the two layers encode differently, passes the check with a public address and connects to a private one.
  2. Literal addresses are tested with `is_private or is_loopback or is_link_local or is_reserved`, which misses the shared range 100.64.0.0/10. A redirect to 100.100.100.200 is followed.
  3. A redirect to a host that a WebFetch deny rule (`WebFetch(domain:…)`) blocks is followed. Permission rules are evaluated for the first URL only.
- **Reproduced (stubbed DNS, servers on 127.0.0.1, mock transports):**
  - `$R/agent_web/fetch_redirect_rebind.py`:
    - `allowed.test/to-cgnat … status=succeeded` reaching `100.100.100.200`;
    - `allowed.test/to-blocked … succeeded` reaching a denied domain;
    - the rebinding case `succeeded getaddrinfo calls for rebind.test=2`, with content from the loopback server.
  - `$R/agent_web/fetch_idna_split.py`: `resolver lookups: ['fass.de', 'xn--fa-hia.de']`, content from the loopback server.
- **Fix:**
  - Resolve once, and accept the answer only when every address satisfies `ip_address(a).is_global`.
  - Connect to that validated address: an httpx transport that dials the pinned IP, keeping the original Host header and TLS server name.
  - Apply the same validation, and the WebFetch permission rules (`engine.decide("fetch_url", {"url": hop})`), to every redirect hop.
  - Literal addresses also use `is_global`.
  - Refuse names that end in `.localhost`, `.local`, `.internal` or `.lan`, and single-label names, and fail closed when resolution fails.
- **Tests:** the four scenarios above with a stubbed resolver: each refused, and the loopback server receives no request.

### W4-R16 — medium — WebFetch has no size bound in its cache, no overall deadline, and leaky page framing

- **Where:** `src/agentos/agentic/tools/web/fetch.py`: the 15-minute cache, `FETCH_TIMEOUT_SECONDS`, and the prompt sent to the answering model.
- **What is wrong:**
  1. The cache stores whole page texts. 64 pages of about 8 MB grew the process by about 515 MB.
  2. The timeout applies per socket operation. A server that sends a byte every few seconds holds the call (and the turn) for as long as it likes, and the turn's cancel flag is never consulted.
  3. The page is wrapped in a fixed `<page>…</page>` delimiter that the page itself can close. When the answering model fails, the raw page is returned to the main model without the "untrusted content" notice.
- **Reproduced:**
  - `$R/agent_web/fetch_cache_memory.py`: `private bytes 73 MB -> 588 MB`.
  - `$R/agent_web/fetch_slow_drip.py`: `returned after 38.3s (FETCH_TIMEOUT_SECONDS=25) … cancel_check consulted 0 times`.
  - `$R/agent_web/fetch_answer.py`: `fallback content labels the page as untrusted? False`, and the provider message shows the page's own closing delimiter.
- **Fix:**
  - Cap each cached text, for example at 512 KB, and the whole cache at 32 MB, with LRU eviction by bytes.
  - Add a total deadline (60 s) to the body read, checking `cancel_check` between chunks.
  - Wrap the page in a per-call random delimiter and remove any occurrence of it from the page.
  - Always prefix the fallback content with the same untrusted notice as the answered path.
- **Tests:** one test per item.

### W4-R17 — medium — the Python Grep fallback and Glob walk into junctions inside the workspace

- **Where:** `src/agentos/agentic/tools/search/grep.py` and `search/glob.py`, the `os.walk` loops. On Windows, `os.walk` descends into junctions; they are not symlinks.
- **What is wrong:**
  - The Python Grep (used when ripgrep is unavailable) reads files under a junction that points outside the workspace and returns their lines.
  - Glob lists their names.
  - Read and ripgrep correctly refuse them.
- **Reproduced:** `$R/agent_web/grep_junction.py`. Python Grep over the workspace returns a line of the outside file; ripgrep gives `[no match]`; Glob lists `linked/secret.txt`; Read refuses.
- **Fix:** in both walks, skip a directory that is a link or junction (`entry.is_symlink()` or `os.path.isjunction`) or whose resolved path is outside its working directory (`resolve_contained`). Apply the same check to files.
- **Tests:** a junction to an outside folder is invisible to Grep (both engines) and Glob.

### W4-R18 — medium — ToolSearch indexes only the first 200 MCP tools

- **Where:** `src/agentos/agentic/tools/mcp/admin.py` `search_mcp_tools`. The `select:` index is built from `engine.search("", limit=200)`, and `+term` filters after the same limit.
- **What is wrong:**
  - With more than 200 MCP tools, `select:` of a later tool reports it under `already_available`, through the built-in branch. It is never activated or published.
  - `+zeta tool` finds nothing for a server sorted after the cap.
  - A `select:` beyond 50 names drops the rest silently.
- **Reproduced:** `$R/agent_web/toolsearch_select.py` and `$R/agent_web/toolsearch_published.py`. `select:mcp__zeta__tool_119 … matches=[] already=['mcp__zeta__tool_119']` and `schema published to the model: False`.
- **Fix:**
  - Build the `select:` index from every document, with no limit.
  - Report a name as `already_available` only when it is a built-in key.
  - Apply `+term` before limiting.
  - Report names beyond the 50 cap under `not_found` with a reason.
- **Tests:** 360 MCP tools: `select:` of the last one activates it, and `+zeta` finds zeta tools.

### W4-R19 — medium — an unavailable directory store fails the whole turn

- **Where:** `src/agentos/agentic/session.py` `_directory_store()`, which builds `ConversationDirectoryStore(engine)` and runs `CREATE TABLE … checkfirst` outside any `try`, and is called by `_conversation_directory_paths` and `_announce_added_directories`.
- **What is wrong:** when the database cannot be written (read-only, locked), building the store raises and `build_runtime` fails, so the turn fails because of an optional feature. It also builds a new store, and runs the table check, twice per turn.
- **Reproduced:** `$R/agent_api/d06_announce_fails_turn.py`: `build_runtime would FAIL here: OperationalError … attempt to write a readonly database`.
- **Fix:** build the store once per session inside the `try` blocks. On failure, log it and continue with no added folders.
- **Tests:** a store constructor that raises: `_apply_working_directories` still sets the settings folders, and the turn builds.

### W4-R20 — medium — file history records failed writes and loses or corrupts manifests under concurrency

- **Where:**
  - `src/agentos/agentic/agent_tools.py` `_snapshot_before_write`, called before the write is validated;
  - `src/agentos/code_mode/file_history.py` `_load` / `_save`.
- **What is wrong:**
  1. A NotebookEdit or Write that then fails (unknown cell, content over the limit) is still recorded. A later rewind of that message restores the file and loses a person's later hand edits to a file the turn never changed.
  2. On Windows, a snapshot taken while another thread reads the manifest fails with a sharing violation and is dropped silently. A later rewind leaves that file changed.
  3. A manifest that fails to load is treated as empty and overwritten, losing its earlier entries and its order.
- **Reproduced:**
  - `$R/agent_history/r06_failed_tool_recorded.py`: `NotebookEdit: failed … history says msg_1 changed: ['analysis.ipynb', 'notes.md'] … hand edit in notebook survives: False`.
  - `$R/agent_history/r07_manifest_sharing_violation.py`: `recorded files: ['a.txt']`, with `b.txt` missing.
  - `$R/agent_history/r08_load_error_resets_manifest.py`: `m1 files now: ['b.txt'] … order: ['m2', 'm1']`.
- **Fix:**
  - Snapshot after validation and immediately before the write. If the write then fails, remove the entry that this call added; keep entries that were already present.
  - `_load` and `_save` retry on `PermissionError` (sharing violation) with a short backoff, up to 1 s.
  - A manifest that cannot be read is never overwritten: snapshots go to a new manifest file for that message, and `rewind` merges the two.
- **Tests:** the three scenarios.
