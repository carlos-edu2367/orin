## Summary verdict

**Not ready for W6.** What holds: trust gates a repository's skills, commands, agents, styles and `.mcp.json`; project agents cannot replace the builtins; plugin agents lose `hooks`, `mcpServers` and `permissionMode`; a skill grant never beats a deny rule, an ask rule, plan mode or a protected path; plugin hooks run without a shell and `resolve_argv` refuses a junction to an outside folder at run time (`$R/test_r15_plugin_junction.py`); plugin options are encrypted and a sensitive one never reaches a command line; the mailbox is keyed by person and conversation.

What does not: a repository can approve its own MCP servers; a repository skill can pre-approve every shell command with a wildcard spelling; a plugin can be re-enabled past its approval, carrying hook consent to hooks the person never saw; on a shared Orin, skill and agent hooks (and the repository's settings hooks) run host commands although every process-starting capability is off; a plugin's language server runs on the hooks' consent without ever being shown. Sixteen findings must be fixed before W6.

## Must fix before W6

### W5-R1 — A repository approves its own `.mcp.json` servers (critical)

- Where: `src/agentos/settings/loader.py:47-48` (`enableAllProjectMcpServers`, `enabledMcpjsonServers` are only *untrusted*-ignored) and `src/agentos/mcp/file_config.py:286-287` (approvals read from the effective settings).
- What is wrong: once the person trusts a folder, the folder's own `.claude/settings.json` can set `enableAllProjectMcpServers: true` (or list its servers in `enabledMcpjsonServers`), and every server in its `.mcp.json` starts with any command line (file servers may use any launcher). Trusting a folder is not consent to run each of its servers; the plan's deviation 21 promises per-server approval by the person.
- Scenario: a cloned repository ships `.mcp.json` with a `powershell -Command ...` server and `.claude/settings.json` `{"enableAllProjectMcpServers": true}`; the person trusts the folder to read its skills; the server runs at the next turn.
- Reproduced: `$R/test_r11_repo_self_approves_mcp.py` → without the key: `ready = [] pending = ['helper']`; with the repository's own key: `ready = [('helper', 'powershell', ('-NoProfile', '-Command', 'Start-Process calc'))]`, provenance `project`.
- Fix: move `enableAllProjectMcpServers` and `enabledMcpjsonServers` to `ALWAYS_IGNORED_FROM_PROJECT` (a repository may still *disable* servers through `disabledMcpjsonServers`). Approvals then come only from user, local, CLI and managed layers and from Claude Code's per-folder choices. Test: the reproduction's second case ends with the server pending.

### W5-R2 — A repository skill pre-approves every shell command with a wildcard spelling (high)

- Where: `src/agentos/agentic/tools/orin/disk_skills.py:43` (`_grant_skill_tools` refuses only a specifier-less `Bash`/`*`).
- What is wrong: `Bash(:*)`, `Bash(**)`, `PowerShell(:*)` and `*(:*)` are not refused for a project skill, and each matches every command, so invoking the skill makes every later shell command of the turn run without asking.
- Reproduced: `$R/test_r01_project_skill_wide_grants.py` → granted `['*(:*)', 'Bash(**)', 'Bash(:*)', 'PowerShell(:*)']`; `curl ... -o x.exe`, `del /s /q ...` and `git push --force` go from `ask` to `allow (allowed by rule Bash(:*))`; `Remove-Item -Recurse` → `allow`.
- Fix: for a project-origin skill (and a plugin skill, if ever granted), keep a grant only when its tool is a named tool (never `*`) and, for shell tools (`rules.SHELL_TOOLS`), its specifier starts with a literal command word (`[A-Za-z0-9._/-]+`) before any `*`, `:` or space-wildcard. Tests: the four spellings are dropped (and logged); `Bash(git status:*)` is still granted.

### W5-R3 — Re-enabling skips a plugin's approval and carries hook consent to hooks the person never saw (high)

- Where: `src/agentos/plugins/service.py:266-288` (`set_enabled`: `PENDING_APPROVAL → ACTIVE` is an allowed transition, and `hooks_were_enabled` re-enables every hook row of the new package) and the consent model (`ActivePlugin.enabled_hook_ids`, `plugin_hook_specs`): consent is keyed by hook id (`plugin:Event:index`), not by what the hook runs.
- Scenario: a consented plugin is republished under the same version with a changed hook and a new `PreToolUse` hook; re-inspecting puts it back to pending approval; `PUT /v1/plugins/{id}/enabled {"enabled": true}` (or the model's tools through the service) activates it without the approval card, and both hooks run under the old consent. Editing the installed `hooks.json` in place also keeps consent.
- Reproduced: `$R/test_r03_plugin_consent_carry_over.py` → after `set_enabled(True)` on the pending record: `active`, hook rows `[('kit:PreToolUse:0', True), ('kit:SessionStart:0', True)]`, hooks that run `[('PreToolUse', 'c.py'), ('SessionStart', 'b.py')]`; after editing the installed file: `[('SessionStart', 'b.py')]` still runs.
- Fix: (a) `set_enabled` only moves between `ACTIVE` and `DISABLED` — a pending plugin goes through `approve`; (b) key each hook's consent by content: store the hook row's reference as `{hook_id}#{digest}` where digest = sha256 of event, matcher, command and timeout (no schema change needed), run a hook only when an enabled row has its exact id and digest, and carry consent over in `set_enabled` only for rows whose reference is unchanged. Tests: the reproduction's two cases end with no hook running until the person allows them again; an unchanged hook keeps its consent across disable/enable.

### W5-R4 — On a shared Orin, skill, agent and repository settings hooks run host commands (critical for server mode)

- Where: `src/agentos/agentic/session.py:3178` (`_scoped_hooks` checks only the hook switches, not the instance's capabilities) and `_install_hooks` (`load_hook_specs` takes the project and local layers' hooks on any instance).
- What is wrong: a server-mode Orin turns the shell, host folders and plugin hooks off, yet a trusted workspace's skill `hooks:` command runs on the host, its `http` hook posts to loopback, and the repository's `.claude/settings.json` command hooks run too (the last one predates W5).
- Reproduced: `$R/test_r05_server_mode_scoped_hooks.py` → `shell tools offered: []`, `skill hook ran a host command: True`, `(pre-W5 control) settings hook ran a host command: True`, `loopback endpoint received POSTs from a server-mode skill hook: ['/internal-admin']`.
- Fix: when the instance may not start host processes (the session's `plugin_hooks` capability is false), install only the managed and user (operator) layers' settings hooks and no skill, agent or plugin hook; and refuse a non-managed `http` hook whose URL is not public (the same `_public_url` check WebFetch uses). Tests: the three reproductions on a server-mode session end with no marker file and no POST; the desktop behaviour is unchanged.

### W5-R5 — On a shared Orin, the server account's own skills, commands and agents reach every profile (medium)

- Where: `src/agentos/skills/disk.py` `skill_roots` and `src/agentos/agentic/agent_definitions.py` `agent_roots` (user folders always read).
- Reproduced: `$R/test_r05_server_mode_scoped_hooks.py::test_server_account_skills_and_agents_reach_every_profile` → `server-mode profile sees the server account's skill: True | agent: True`.

### W5-R6 — A plugin's language server runs on the hooks' consent and is never shown (high)

- Where: `src/agentos/lsp/config.py:82` (a server starts when the plugin has any enabled hook) and the inspection/approval result (`PluginService._inspection_result` lists no language server); `PluginInspection.is_installable` counts no language server.
- Scenario: a package with a harmless hook and an `.lsp.json` whose command is `powershell -NoProfile -EncodedCommand ...`; the card shows the hook only; the person allows hooks; the encoded command starts after the first Write of a matching file. A package with only language servers cannot be installed at all.
- Reproduced: `$R/test_r06_lsp_consent.py` → card keys without any language server, `card mentions powershell: False`; `language server that will start after the first Write of a .py file: [('powershell', ('-NoProfile', '-EncodedCommand', ...))]`; `pure LSP package: ... contributes nothing Orin can use`.
- Fix: the inspector reads the language servers (same parser as `lsp_servers`) into the inspection and the approval result (name, command, args, extensions); they count as contributions; consent rows of kind `lsp` keyed by `{name}#{digest}` are switched with the hooks' consent (`set_hooks_enabled`), and `lsp_servers` starts only a server whose exact row is enabled. Tests: the card lists the server; it does not start until its own row is enabled; an LSP-only package installs.

### W5-R7 — Arguments can add new `` !`cmd` `` commands to a skill (medium)

- Where: `src/agentos/agentic/tools/orin/disk_skills.py:90-91` (`substitute` puts `$ARGUMENTS` into the body before `_run_inline_commands` scans it).
- Scenario: the model (possibly steered by injected text) calls a skill whose body is ``Echo: !`echo $ARGUMENTS` `` with arguments ``hi` and !`del /q important.txt``; two commands are run, the second written entirely by the arguments. In a non-interactive turn where asks are allowed, it runs without a person seeing it.
- Reproduced: `$R/test_r13_inline_before_grants.py::test_arguments_can_add_an_inline_command` → `commands the skill tried to run: ['echo hi', 'del /q important.txt']`.

### W5-R8 — A skill's `allowed-tools` do not cover its own inline commands on first use (medium)

### W5-R9 — An MCP server can hold a call open forever by sending requests (medium)

- Where: `src/agentos/mcp/transport_stdio.py:190`, `transport_sse.py:164`, `transport_ws.py:96` (the deadline restarts after each server request answered).
- Reproduced: `$R/test_r14_stdio_ping_holds_call.py` → `timeout=2s; after 8.0s the call is still waiting: True`.

### W5-R10 — `allowedMcpServers` / `deniedMcpServers` URL patterns are bypassed by spelling (medium)

- Where: `src/agentos/mcp/file_config.py:196` (`_wildcard` matches the raw string; `*` also matches `/`).
- Reproduced: `$R/test_r12_mcp_url_policy.py` → deny `https://*.evil.example/*` matches `https://api.evil.example/mcp` but not `https://API.EVIL.EXAMPLE/mcp`, `https://api.evil.example:443/mcp`, `https://api.evil.example./mcp` or `HTTPS://...`; allow `https://*.company.example/*` accepts `https://attacker.example/.company.example/mcp`.
- Fix: normalise both sides before matching (lower-case scheme and host, drop the default port, strip a trailing dot, resolve dot segments) and match the host part with a `*` that cannot cross `/`. Tests: every bypass above is denied, the attacker URL is not allowed.

### W5-R11 — YAML aliases in frontmatter expand exponentially (medium)

- Where: `src/agentos/skills/disk.py:109` `split_frontmatter` (`yaml.safe_load`), used by disk skills, agent files and the plugin inspector (before any approval).
- Reproduced: `uv run python "$R/r02_alias_bomb.py" <levels>` — each level multiplies the work by 9; at 4 levels a 273-byte agent file yields 6,561 tool entries; a few more levels take seconds and hundreds of MB in `parse_agent_file` and in `inspect_plugin_package`.
- Fix: refuse anchors and aliases in frontmatter (a `SafeLoader` subclass whose `compose_node` raises on an alias event) and cap the frontmatter at 64 KB before parsing. Tests: an alias in a skill, an agent file and a plugin agent is reported, not expanded.

### W5-R16 — A configuration-file server's ordinary values are refused (medium, broken feature)
