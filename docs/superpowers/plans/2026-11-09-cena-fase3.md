# Cena, Fase 3: parar e mandar mensagem a um subagente específico

Data: 2026-11-09 · Spec: `docs/superpowers/specs/2026-11-09-cena-pixel-art-design.md` (itens 9, 10 e 11)

## Por que o desenho é assim (fatos verificados no código)

- O turno roda em **outro processo**: `launcher/internal.py` sobe `agentos.workers.publisher.main`, que cria o
  `ChatWorker`. A API (`api/gateway.py`) não enxerga a memória do worker. Por isso `BACKGROUND_AGENTS`
  (`agentic/background_agents.py`), que é um singleton em memória, **não serve** como canal API → worker.
  O `/cancel` já funciona assim: a API grava `state="cancelling"` no banco (`chat.py:request_cancel`) e o
  worker consulta `store.cancel_requested(turn_id)`.
- Só subagentes em background (e os síncronos "promovidos") têm um `threading.Event` de parada
  (`hook_cancel`). Um subagente síncrono comum roda com `hook_cancel=None` (`session.py:2771-2786`), então hoje
  não há como pará-lo sozinho.
- O predicado de cancelamento de um subagente é `self._child_cancelled(hook_cancel, caller)`
  (`session.py:4967`). Ele já combina o do pai com o evento próprio, e os filhos usam esse predicado como
  `caller.cancelled`. Logo, parar um agente para tudo o que ele iniciou.
- Cada subagente tem a própria `ReminderQueue` (`sub_reminders`, `session.py:3311`), drenada antes de cada
  requisição ao modelo. É por ali que uma mensagem chega ao subagente em execução.
- `agent_id` tem o formato `agent:{conversation_id}:{24 hex}`, com mais de 64 caracteres. Por isso
  **não dá** para reaproveitar `agent_mailbox` (`recipient` é `String(64)`).
- As migrações ficam em `src/agentos/persistence/postgres/migrations/versions/`; a última é `0057_user_agents.py`.

## Desenho

### Backend

1. **Tabela nova `conversation_agent_controls`** (schema + migração `0058_conversation_agent_controls.py`,
   idempotente como a 0057):
   `id` (PK int), `control_id` (String 255, único), `conversation_id` (255), `user_id` (255),
   `agent_id` (255), `kind` (String 16: `stop` | `message`), `content` (Text, vazio para stop),
   `created_at`, `consumed_at` (nullable), `outcome` (String 16, nullable: `delivered` | `stopped` |
   `expired` | `forwarded`). Índice `(conversation_id, agent_id, consumed_at)`.
2. **`src/agentos/conversations/agent_controls.py`**, no padrão de `mailbox.py`: `AgentControlStore(engine)` e
   `InMemoryAgentControls` com a mesma interface:
   - `request_stop(user_id, conversation_id, agent_id) -> str`, idempotente: se já houver um stop pendente,
     devolve o id dele;
   - `post_message(user_id, conversation_id, agent_id, content) -> str` (strip, de 1 a 8000 caracteres);
   - `take(user_id, conversation_id, agent_id) -> list[dict]`: pendentes em ordem, marcados como consumidos
     (`consumed_at`), e o chamador define o `outcome`;
   - `expire_pending(user_id, conversation_id, agent_id) -> list[dict]`: marca os pendentes como `expired` e
     devolve quais eram.
3. **Rotas** em `api/gateway.py`, perto do `/cancel` e no mesmo estilo:
   - `POST /v1/conversations/{conversation_id}/agents/{agent_id}/stop` → 202 `{agent_id, status: "stopping", control_id}`.
     Usa `principal_for(request, mutable=True)` e `authorize(action="conversation.cancel", ...)`, como o `/cancel`.
   - `POST /v1/conversations/{conversation_id}/agents/{agent_id}/messages` com corpo `{message}` (modelo Pydantic,
     `min_length=1`, `max_length=8000`) → 202 `{agent_id, status: "queued", control_id}`, com
     `authorize(action="conversation.send", ...)`.
   - Ambas passam pela aplicação de conversa (`conversations/chat.py`, a classe da linha ~3200 que tem
     `cancel`), com métodos novos `request_agent_stop(conversation_id, user_id, agent_id)` e
     `send_agent_message(conversation_id, user_id, agent_id, message)`. Validações, nesta ordem:
     a) a conversa é do usuário (senão `ApplicationNotFoundError`, que vira 404);
     b) a linha em `conversation_agents` tem esse `agent_id`, esse `conversation_id` **e** esse `user_id`
        (senão 404, para não revelar agentes de outra conversa);
     c) `state` em (`running`, `working`); senão, conflito 409 com código `AGENT_NOT_RUNNING` (use a exceção de
        conflito que o projeto já mapeia para 409; procure em `api/` como o 409 é gerado);
     d) grava o controle.
   - Se o `ConversationApplication` estiver declarado em `api/contracts.py` como Protocol, acrescente os dois
     métodos lá.
   - Inclua as duas rotas nas listas de `tests/integration/api/test_profile_isolation.py`, se esse teste exigir
     cobertura de toda rota mutável.
4. **Worker / sessão** (`agentic/session.py`), com a menor mudança possível:
   - Em `_execute_subagent_run_inner`, **antes** do teste de cancelamento pré-execução:
     - se `hook_cancel is None`, crie um `threading.Event()` local, para que todo subagente tenha um ponto de
       parada próprio;
     - crie um `_AgentControlWatcher` para esse `agent_id`, que expira os controles pendentes antigos
       (`expire_pending`), para que um stop que sobrou de uma execução anterior não mate uma retomada;
     - passe evento e watcher adiante, para `_execute_subagent_run_unlocked`.
   - `_AgentControlWatcher.poll()` é **limitado a uma consulta por segundo** (`time.monotonic`) e nunca levanta
     exceção: erro de banco vira `logger.debug` e a execução segue. Em cada `poll`, faz `take` e trata:
     - `stop`: marca `outcome="stopped"`, liga a flag `stopped_by_user` e faz `event.set()`;
     - `message`: `sub_reminders.add("user_message", f"Message from the user (sent to you directly while you work):\n{content}", key=f"user-msg:{control_id}")`
       com `outcome="delivered"`. Grave também uma atividade com
       `AgentActivityEventType.AGENT_MESSAGE_SENT`, título `"Você enviou uma mensagem para {clean}"` e payload
       `{agent_name, recipient_name: clean, sender_name: "Você", label: clean, content: content[:PREVIEW_CHARS], to_agent_id: agent_id, source: "user", tool_kind: "agent"}`,
       com `agent_id=agent_id`.
   - O predicado: `_child_cancelled` ganha um parâmetro opcional `watcher=None`. Com o watcher, o predicado chama
     `watcher.poll()` antes de checar o evento. Assim o mesmo ponto que já é consultado o tempo todo também traz
     as mensagens. Sem watcher, o comportamento continua idêntico.
   - Quando o run termina, no `finally` do inner, o watcher faz um `take` final:
     - stops que sobraram → `expired`;
     - mensagens que sobraram → `outcome="forwarded"`, e vão para o agente principal como
       `self._reminders.add("user_message", f"The user sent this to subagent {clean} ({agent_id}), which finished before reading it:\n{content}", key=...)`.
   - Parado pelo usuário: se `stopped_by_user` estiver ligada e o run terminar cancelado, o `reason` / `error_code`
     do `DELEGATION_FAILED` e do `ToolOutcome` vira **`STOPPED_BY_USER`**, no lugar de `TURN_CANCELLED`. O conteúdo
     para o modelo pai diz:
     `"The user stopped subagent '{clean}' from the interface. Do not restart it unless the user asks."`,
     seguido do resumo parcial que `_format_subagent_partial_failure` já produz. `final_agent_state` = `"cancelled"`.
     Em `_run_background_agent` e no worker promovido, `bg_status` continua `"stopped"`, porque o evento está
     ligado. Confira que `STOPPED_BY_USER` não cai em nenhum caminho que trate o turno inteiro como cancelado.
   - O store vem do mesmo jeito que `_team_mailbox()`: `AgentControlStore(self.chat_store._engine)`, ou
     `InMemoryAgentControls()` sem engine, com cache em `self._agent_controls_store`. `user_id` e
     `conversation_id` vêm de `self.turn`.
5. **Testes pytest** (novos):
   - `tests/unit/conversations/test_agent_controls.py`: store em SQLite em memória e InMemory, com post, take,
     idempotência do stop, expire e isolamento por `user_id` / `conversation_id`;
   - `tests/unit/agentic/test_subagent_user_controls.py`, seguindo o estilo de `test_background_agents.py` e
     `test_nested_subagents.py`. Deve cobrir:
     a) um stop gravado durante um subagente **síncrono** faz ele parar, o pai recebe `STOPPED_BY_USER` e o turno
        principal **continua**;
     b) uma mensagem gravada chega ao `ReminderQueue` do subagente e gera o evento `AGENT_MESSAGE_SENT` com
        `source="user"`;
     c) um stop antigo pendente não mata uma retomada (`expire_pending`);
     d) uma mensagem que sobra no fim vai para os reminders do principal;
     e) parar um agente para os filhos dele;
     f) o throttle de 1 segundo, com relógio injetável ou monkeypatch de `time.monotonic`;
   - testes de rota (siga o padrão do teste de `/cancel` em `tests/unit/agentic/test_background_agents.py:429`
     ou dos testes de API em `tests/integration/api/`): 202 no caminho feliz, 404 com agente de outra conversa,
     404 com conversa de outro usuário, 409 `AGENT_NOT_RUNNING` com agente `completed`, 422 com mensagem vazia
     ou com mais de 8000 caracteres.

### Frontend

6. **API**, em `frontend/src/api/conversations.ts` e no estilo de `cancelConversation`:
   `stopConversationAgent(client, conversationId, agentId, intent?)` e
   `sendConversationAgentMessage(client, conversationId, agentId, message, intent?)`, com `encodeURIComponent`
   no `agentId` (ele tem `:`), `expectedStatus: 202` e parse defensivo.
7. **Reducer da Cena** (`scene/sceneReducer.ts` e `sceneTypes.ts`):
   - um `DELEGATION_FAILED` com `errorCode` / `error_code` `STOPPED_BY_USER` deixa o agente com o status novo
     `stopped` (rótulo "parado por você"), pose `idle`, sem alarme, sem `scared`, sem efeito de erro. Inclua
     `stopped` em `SceneAgentStatus` e confira os `switch`es exaustivos (HUD, canvas, sprites);
   - um `AGENT_MESSAGE_SENT` com `source === 'user'` vira um balão `speech` no agente destino
     (`"Você: …"`, sanitizado e cortado como os outros), **sem** envelope / transfer do Orin. Confira como os
     eventos chegam ao frontend (camelCase ou snake_case no `payload`) lendo `activityTypes.ts` e o reducer
     atual de mensagens.
8. **Painel do personagem** (`scene/SceneHud.tsx`), **só para subagentes** (`!agent.isMain`):
   - com status `working`, `thinking`, `waiting_agent`, `waiting_user` ou `queued`, aparecem os botões
     **"Parar"** e **"Mensagem"**;
   - **"Parar"** pede confirmação inline ("Parar {nome}? Ele interrompe o que está fazendo e para os agentes que
     ele iniciou." com "Parar agora" / "Cancelar"). Ao confirmar, chama `onStopAgent(agentId)`. Enquanto
     espera, o rótulo vira "parando…". Se falhar, aparece o erro em texto (`role="alert"`);
   - **"Mensagem"** abre um campo (textarea + "Enviar" + "Cancelar", Enter envia e Shift+Enter quebra linha) e
     chama `onMessageAgent(agentId, text)`. Se der certo, aparece "Mensagem entregue a {nome}; ele lê no próximo
     passo." Se der 409 `AGENT_NOT_RUNNING`, aparece "{nome} já terminou." com o botão
     **"Pedir ao Orin para retomá-lo"**, que chama o `onSendToOrin` já existente (Fase 2) com
     `Retome o agente "{nome}" (agent_id {id}) com esta mensagem: {texto}`. Outro erro mostra a mensagem em texto;
   - com o agente parado, terminado ou falho, os botões não aparecem;
   - acessibilidade: botões com `aria-label` explícito, foco vai para o textarea ao abrir, Esc fecha.
9. **Ligação**: `SceneView` recebe e repassa `onStopAgent` e `onMessageAgent` (opcionais; sem eles, os botões
   não aparecem). O `ChatPage` implementa os dois com `createBrowserApiClient()`, no mesmo padrão dos outros
   handlers, e mapeia o `ApiError` com status 409 / code `AGENT_NOT_RUNNING` para um resultado tipado
   (por exemplo `{ ok: false, reason: 'not_running' }`), que o HUD usa.
10. **Testes vitest**:
    - reducer: `STOPPED_BY_USER` vira `stopped` sem alarme; mensagem do usuário vira balão sem transfer;
    - `SceneView` / `SceneHud`: os botões aparecem só para subagente ativo; parar exige confirmação; a mensagem
      envia; o 409 mostra "Pedir ao Orin para retomá-lo", que chama `onSendToOrin` com o texto esperado;
    - API: o path usa `encodeURIComponent`.
11. **Spec**: atualize o `Status` para "Fases 1, 2 e 3 implementadas" e marque as linhas 99-100 da tabela
    "Ações da Cena" como ✅, com as rotas novas.
